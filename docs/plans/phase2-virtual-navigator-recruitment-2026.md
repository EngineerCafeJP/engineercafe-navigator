# Part A. 役割別 詳細募集要項（内部設計兼）

## 1. プロジェクト概要（Phase 2 ビジョン）

Phase 1 で立ち上げた「EngineerCafe Navigator」（LangGraph ベース AI エージェント）を、
**クラウド依存からオンプレミス（ミニPC／自前サーバー）へ移行**し、
**受付システム・IoT・UI・バックエンドを一体統合した次世代「バーチャルナビゲーター」へリプレース**する。

### 3つの柱

1. **コスト構造の転換** — Cloud Run 常時起動の従量課金を、オンプレ＋ローカルLLMで大幅圧縮する
2. **受付体験の完全統合** — 来場者が「話しかける／会員証を見せる／NFCカードをかざす」だけで受付が完結する IoT × AI 受付
3. **疎結合アーキテクチャ** — バックエンドとフロントエンドを API 契約で分離し、UI を React 軽量化や Unity 等へ差し替え可能にする

---

## 2. なぜオンプレ化か（コスト根拠）

### 2.1 現状の Cloud Run 実機構成（`gcloud` 確認済み）

| サービス | リージョン | 構成 | スケール | CPU課金 |
|---|---|---|---|---|
| `engineer-cafe-backend` | asia-northeast1 | 4 vCPU / 8Gi・**concurrency=1** | **minScale=5 / maxScale=15** | 常時割当 (throttling=false) |
| `piper-plus` (TTS) | asia-northeast1 | 2 vCPU / 2Gi | **minScale=2 / maxScale=10** | 常時割当 |
| `voicevox-proto` (TTS) | asia-northeast2 | 4 vCPU / 2Gi | scale-to-zero / maxScale=12 | — |

### 2.2 月額試算（構成 × Cloud Run Tokyo 公開単価・実請求額は未検証）

> 単価: vCPU $0.0000180/s・Memory $0.0000020/GiB-s（CPU常時割当）／月=2,592,000秒

- `engineer-cafe-backend` 常時5台ベースライン: **約 $1,140/月**
  - vCPU: 5 × 4 × 0.0000180 × 2,592,000 ≈ $933
  - Mem: 5 × 8 × 0.0000020 × 2,592,000 ≈ $207
- `piper-plus` 常時2台: **約 $207/月**
- **ベースライン（アイドル時・最小構成）だけで 約 $1,350/月 ≈ ¥20万/月**

これに加えて以下が乗る:
- オートスケール時の追加インスタンス（backend→15・piper→10・voicevox→12）
- OpenRouter LLM トークン従量
- OpenAI embeddings 従量
- Supabase（Pro 〜$25/月＋従量）
- Vercel（フロント）
- egress（下り通信）

→ **現実的には月 ¥25〜35万、年間 ¥300〜420万規模（試算）**

### 2.3 オンプレ移行後の見込み

- ミニPC／ワークステーション: **一回 ¥20〜60万の初期投資**（GPU有無で変動）
- 電気代: 月 ¥3,000〜10,000 程度
- **数ヶ月で初期投資をペイ。以降のランニングは電気代＋クラウド補完の少額API従量のみ**

> ⚠️ ただしオンプレ化は「サーバー代をハード代に置き換える」だけではなく、**運用責任（死活監視・バックアップ・物理障害対応・ネットワーク）がチーム側に移る**。この運用コストを IoT 枠で見込む。

## 3. アーキテクチャ方針

### 3.1 LLM 戦略 — ローカルファースト＋クラウド補完（ハイブリッド）

**方針**: できる限りローカルLLMで処理し、高度な推論を要する部分のみ OpenRouter 等のクラウドAPIで補完する。

既存バックエンドには **二段階LLMルーティングの env が既に存在**（`FAST_LLM_PRIMARY/FALLBACK/TERTIARY`・`DEEP_REASONING_MODEL`・`CEREBRAS_*`）。**この設計をそのまま活かせる**のが大きい。

| 階層 | 用途 | 移行後の担い手 |
|---|---|---|
| **FAST（軽量・定型）** | intent分類 / keyword routing / 定型FAQ / 短い応答 | **ローカルLLM**（Ollama / llama.cpp。例: Qwen2.5-3B/7B, Gemma, ELYZA-JP 系を比較検証） |
| **DEEP（高度推論）** | 複雑なRAG回答 / GeneralKnowledge / 難しい多言語 | **クラウド維持**（OpenRouter / Cerebras をフォールバック） |
| **Embedding** | KB検索の埋め込み | **当面クラウド維持**（従量が極小。ローカル化＝KB全再埋め込みが発生するため後続評価） |

> 📌 **重要な制約**: 現在の埋め込みは `text-embedding-3-small`（1536次元）固定。ローカル埋め込み（bge-m3 等）へ替えると **`knowledge_base` 全件の再埋め込み＋RPC修正**が必要。初期スコープからは外し、Phase 2-C 以降の評価項目とする。

### 3.2 データ基盤 — Supabase → セルフホスト PostgreSQL

- pgvector を有効化したセルフホスト PostgreSQL へ移行（docker-compose に `pgvector 16` 既存）
- RLS / service_role パターンの再現 or postgres ネイティブRLSへの置き換え方針を要件定義
- LangGraph checkpoint / store の保存先を `SUPABASE_DB_URI` からローカルDBへ
- マイグレーション管理: supabase CLI → alembic/flyway 等への移行を検討

### 3.3 外部依存の扱い（オンプレ時の分岐点）

| 依存 | 現状 | 方針 |
|---|---|---|
| OpenRouter (LLM/embedding) | 必須 | DEEP推論のみ維持。FASTはローカル化 |
| Supabase | DB/Auth/RLS | セルフホストPostgreSQLへ |
| Google Calendar | public ICS feed | CalDAV / ローカル ics 取り込みへ要検討 |
| Tavily (web検索) | GeneralKnowledge fallback | オフライン時は縮退。必要なら自前クローラ |
| Connpass API | イベント取得 | 公開APIのため維持可 |

### 3.4 フロントエンド分離 — API 契約ファースト

- 現状 `frontend/src/lib/api/backend-proxy.ts` の `backendFetch()` は **純粋HTTPプロキシ**。UI差し替え余地は高い。
- ただしページロジックが backend のレスポンス形状に依存。**API契約（スキーマ＋バージョニング）を明文化**してから UI を切り離す。
- **スタック選定はプロジェクトの最初のタスク**（打ち上げメモ「フロントエンドの改修(どのスタックで行くか)」）。
  - 候補: Next.js継続 / Vite+React軽量化 / （将来）Unity等への差し替え視野
  - 判断軸: バンドルサイズ・キオスク端末性能・3D(VRM/Three.js)の継続性・オフライン動作
