# ADR-005: ロジックをバックエンド側に集約する方針

## Status

Accepted (2026-03-25)

## Context

Engineer Cafe Navigatorは現在Next.js（フロントエンド）+ FastAPI（バックエンド）構成だが、将来的にフロントエンドをUnity等に置き換える可能性が高い。

現状、一部のロジック（キャラクター制御のHTTPメソッド判定、感情タグの処理等）がフロントエンドに依存しており、フロントエンドをリプレースする際に再実装が必要になる。

### 具体的な問題

1. **GET /api/character 405問題**: フロントエンドがGETで呼び出すが、バックエンドはPOSTのみ対応。フロントエンド側でPOSTに変更するよりバックエンド側でGETを受け付けるべき。
2. **感情タグ除去**: LLM応答に`[relaxed]`等のタグが混入。フロントエンドで除去するのではなく、バックエンドで除去してクリーンなテキストを返すべき。
3. **音声再生**: TTS処理はバックエンドで完結しており、フロントエンドは再生のみ。この分離は正しい。

## Decision

**ビジネスロジック・データ処理はバックエンドに集約し、フロントエンドは純粋なUIレイヤーとして維持する。**

### 原則

1. **バックエンドはクライアント非依存のAPIを提供する**: HTTP標準に従い、GET/POST両方をサポートする等、特定のフロントエンド実装に依存しない
2. **データのクリーニング・変換はバックエンドで完結する**: LLM応答の感情タグ除去、レスポンスフォーマットの正規化等
3. **フロントエンドはAPI応答をそのまま描画する**: フロントエンド側でのデータ変換を最小限にする
4. **フロントエンド固有の責務**: UI描画、AudioContext管理、ブラウザAPI（カメラ、マイク等）の制御のみ

### 適用範囲

| 責務 | 担当 | 理由 |
|------|------|------|
| LLM応答の整形 | Backend | クライアント非依存 |
| 感情タグの除去 | Backend | データクリーニング |
| VRM制御データ生成 | Backend | エージェントロジック |
| HTTPメソッドの柔軟な対応 | Backend | クライアント非依存API |
| AudioContext初期化 | Frontend | ブラウザ固有API |
| カメラ/マイク制御 | Frontend | デバイス固有API |
| UI描画・アニメーション | Frontend | プラットフォーム固有 |

## Consequences

### Positive

- フロントエンドをUnity、Flutter、ネイティブアプリ等に置き換える際の再実装コストが最小限
- バックエンドAPIの動作がフロントエンドの実装詳細に依存しない
- テストがバックエンド側で完結し、フロントエンド変更によるリグレッションリスクが低い

### Negative

- バックエンドの変更がフロントエンドの動作に直結するため、デプロイ順序に注意が必要
- バックエンドの責務が増え、コードベースが大きくなる

### Neutral

- 既存のプロキシパターン（`backendFetch()`）は維持。フロントエンドはプロキシとして機能し続ける
